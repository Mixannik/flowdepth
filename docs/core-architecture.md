# Рабочее ядро Flowdepth

Статус: план от 01.11.2026; A1, A2a и A2b реализованы и проверены: 495 тестов прошли, 12 пропущены. В рабочий терминал изменения не установлены. A3 и следующие этапы ещё не реализованы.
Приоритет владельца: сначала надёжное ядро, затем новые функции.
Ядро должно поддерживать свободно настраиваемое рабочее место полноценного терминала: `docs/terminal-workspace.md`. UI — отдельное направление развития, не заключительная косметическая правка.

## Что сейчас

Основа уже модульная: exchange, data, indicator-engine, connector, trait KlineIndicatorImpl.
Проблема — ответственность пересекает границы:

- Глобальный `SIZE_CALC_UNIT` в exchange влияет на входные количества; предпочтение отображения становится свойством данных.
- `data` совмещает доменные структуры с iced_core, конфигурацией интерфейса и файловым сохранением.
- KlineChart совмещает загрузку, модель, вычисления профиля, сигналы и рисование.
- Dashboard отвечает и за видимость панели, и за её tick. Максимизация может приостановить фоновые запросы.
- Индикаторы имеют единый trait, но транспортные FetchRange и UI-методы уже входят в него.
- Время, покрытие, происхождение и точность результата не образуют общего контракта между слоями.

Это накопленные связи, а не необходимость выбросить существующую реализацию.
Цель рефакторинга — проверяемые границы, а не число crates или сокращение строк.

## Целевые границы

| Часть | Владеет | Не должна решать |
|---|---|---|
| Профиль и хранение | Путь профиля, lock, state, версии, снимки, ошибки записи | Как считать индикатор |
| Модель рынка | Инструмент/рынок, UTC-время, цена, явные единицы и данные контракта | Цвет, видимая вкладка, предпочтение BTC/USD |
| Сервис данных | Live/history/cache, диапазоны, дедупликация, покрытие и источники | Координаты графика и видимость панели |
| Расчёты | Свечи, профили, CVD, сигналы из входных данных | Сеть, файловая система, iced |
| Сценарии приложения | Потребности панелей, подписки, доставка результатов, жизненный цикл | Формулы индикаторов и пиксели |
| Представление | Оси, цвет, масштаб, формы и действия пользователя | Исправление пропусков данных подстановкой достоверного нуля |

Существующие exchange/data остаются на переходный период. Новые crates создавать только когда граница уже выделена и её можно проверить отдельно.

## Правила ядра

1. Одни рыночные данные дают одинаковые расчёты при live, backfill и чтении кэша. Отличия из-за сжатия явно описаны и проверяются.
2. Выбор BTC/USD для показа не изменяет сохранённые данные. Для обратных контрактов использовать спецификацию инструмента; не считать все количества BTC.
3. Нет данных, нулевое значение, неполный диапазон и приближённый расчёт различаются.
4. Каждый результат имеет диапазон времени и статус покрытия. Для сигналов отдельно время события и подтверждения.
5. Открытие/закрытие/масштабирование панели не меняет смысл расчёта. Таймер доставки данных независим от рисования.
6. Ошибка блокировки/доступа не является доказательством повреждения. Оригинал не удаляется ради успешного запуска.
7. Неподдерживаемая версия state не должна автоматически уничтожать неизвестные блоки.
8. Ресурсы ограничены: сроки хранения, очереди и отмена запросов имеют владельца и проверяемую политику.

## Переход небольшими этапами

### A. Основание: профиль и сохранность

Выделить разрешение путей профиля и операции сохранения за отдельные модули, не переносить одновременно всю модель.
Начать с различения ошибок открытия кэша; затем безопасная Windows-замена state и неразрушительное recovery.
Ввести lock на профиль до чтения state/открытия кэша. Отдельный тестовый профиль должен включать state, cache и logs.
Не внедрять автосохранение поверх старой небезопасной записи.

Готово, когда: второй экземпляр не меняет файлы первого; отказ записи оставляет читаемую предыдущую версию; неизвестная панель переживает загрузку; тестовый запуск не касается рабочего профиля.

### B. Контракт рыночных данных

Определить явные единицы хранения и конвертации для spot/linear/inverse.
Сначала тесты на синтетических сделках и реальные сохранённые примеры, затем изменение нормализации и версия кэша.
Описать покрытие и происхождение raw/aggregate/candle approximation. Проверить независимость результата от границ порций загрузки.

Готово, когда: переключение отображения не меняет данные; целая минута и две её части дают одинаковые объём/дельту; live/cache/backfill проходят один набор контрольных примеров.

### C. Расчёты отдельно от графика

Взять один ограниченный пример (period levels), выделить чистые вход/выход и проверку покрытия.
Оставить UI-адаптер совместимым с KlineIndicatorImpl. Затем переносить VWAP/профили/CVD по одному, без общего переписывания.
Сигналы должны иметь явную политику предварительного/подтверждённого состояния и исторические зависимости.

Готово, когда: пример рассчитывается без запуска окна/сети; неполный месяц не выдаётся за полный; перерисовка не пересчитывает смысловую модель.

### D. Общий жизненный цикл данных

Отделить потребности в данных от видимости панелей. Сначала измерить повторные запросы; затем переносить их координацию в сервис данных.
Сохранить существующее объединение WebSocket-подписок. Не строить новый универсальный event bus без конкретной потребности.

Готово, когда: две одинаковые панели используют общую загрузку где это безопасно; максимизация/смена вкладки не останавливают обновления; закрытая панель освобождает свою потребность и ненужные задачи.

## Первый пакет реализации

Только A1: типизированное различение ошибок открытия redb, отказ от карантина на lock/permission/неопределённую IO-ошибку, регрессионная проверка на временной базе с двумя открытиями.
Не менять в этом пакете формулы, визуализацию, формат кэша и рабочие настройки.
Следующие пакеты A2 (state), A3 (профили/lock) идут отдельно: так проверяем каждый отказ и можем вернуться на предыдущую сборку.

## Как принимать архитектурную работу

Для каждого пакета фиксировать: какую связь убрали, какое поведение сохранили, какой сценарий отказа теперь проверяется.
Перенос функций между файлами сам по себе не считается укреплением ядра.
До установки — тесты на копиях и отдельный профиль; рабочий терминал обновляется отдельным действием.
