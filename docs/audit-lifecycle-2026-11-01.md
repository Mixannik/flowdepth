# Аудит жизненного цикла и сохранности Flowdepth — 01.11.2026

Статический разбор текущей feat/delta-table. Приложение не запускалось, реальные state/кэш не менялись, сеть не использовалась. Причина прошлого повреждения по одному коду не установлена. Тесты не запускались: ниже оценка реализации и имеющегося покрытия.

## Как устроено

- `src/main.rs:329`: загрузка state через `layout::load_saved_state`; состояния Loaded/Missing/Migrated/Recovered/Corrupt обрабатываются отдельно. При Corrupt запись запрещена до решения пользователя (`src/main.rs:359`, `1228`).
- `data/src/lib.rs:171`: JSON читается, проходит нормализацию/очистку, десериализуется; создаются резервные копии при миграции и восстановлении. Новый номер формата отклоняется (`211`).
- `src/main.rs:2325`: события отправляются активной раскладке и всем раскладкам с нужным потоком; `2350` собирает объединение потоков, `2215` строит общие подписки.
- `src/main.rs:923`: после загрузки активной раскладки запускается фоновый tick остальных; `904` раз в секунду синхронизирует уровни FRVP. `src/screen/dashboard.rs:2658` обрабатывает таймеры панелей и их запросы данных.
- `src/main.rs:2952`: сериализуются все раскладки, настройки, тема, окно и прочее. Сохранение при штатном выходе (`1048`), перезапуске (`1068`) и отдельных изменениях сети (`1595`, `1633`). Общего периодического автосохранения раскладок в изученном пути нет.
- `.github/workflows/develop-ci.yml:1`: форматирование, check, clippy, workspace tests и проверка индикаторных исходников, затем упаковка трёх платформ и публикация. Push-триггер ограничен develop; прямые push в feat/delta-table автоматически не проверяются этим workflow.

## Подтверждённые риски и порядок исправления

1. **P1 — Windows-сохранение не атомарно.** `data/src/lib.rs:337`: сначала удаляется конечный state, затем выполняется rename; при неудачном rename удаляется временный файл (`343`). Между операциями есть окно без основного файла. Следующий запуск при отсутствии state выбирает default (`177`), а rolling backup автоматически не загружается. Резервная копия обычно остаётся, но требуется ручное восстановление. Нужна замена файла через Windows API с гарантией сохранения старого при отказе; тесты на отказ операции, не только успешный путь.
2. **P1 — восстановление перезаписывает исходный state ещё на старте.** `data/src/lib.rs:273–277`: неизвестные части очищаются и результат сразу записывается; создание backup вызывается через `.ok()`, его неудача запись не блокирует. Неизвестная панель заменяется на Starter (`676`), индикатор удаляется при ошибке Deserialize (`833`). Поэтому несовместимая сборка способна превратить доступный для будущей версии state в обеднённый файл. Это подтверждённый механизм риска, а не доказанная причина инцидента. Нужны обязательная успешная копия и сохранение исходного JSON/неизвестных блоков без разрушения при чтении.
3. **P1 — два процесса используют общие файлы.** В проверенных src/data/Cargo.toml не найден контроль одного экземпляра. `data/src/lib.rs:316` всегда использует один `saved-state.json.tmp`, `331` — одну rolling-копию. Два процесса могут затирать состояние друг друга и сталкиваться в записи. Нужен процессный lock до чтения state и открытия кэша; второй запуск должен активировать существующее окно либо завершаться с понятным сообщением. Изолированные профили нужны и для тестового терминала.
4. **P2 — ошибка сохранения не останавливает выход.** `src/main.rs:3006`: ошибка только логируется; `1057` всё равно завершает приложение. Нужен видимый выбор повторить/сохранить в другой файл/выйти, с сохранением данных в памяти до решения пользователя.
5. **P2 — ограниченная история копий.** `data/src/lib.rs:33`: хранится всего 5 файлов; `897` удаляет самые старые файлы по широкому шаблону `saved-state.*.json`, включая миграционные/восстановленные копии. Rolling backup также попадает в этот набор. Нужны отдельные классы: частые автокопии с ротацией и защищённые предмиграционные/предустановочные снимки.
6. **P2 — несохранённые изменения между выходами.** Общего автосохранения не обнаружено; падение/принудительное завершение теряет изменения раскладок после последнего сохранения. Нужен debounce после изменений плюс периодический снимок, но только после исправления пунктов 1–3.
7. **P2 — maximized скрывает tick других панелей.** `src/screen/dashboard.rs:2739`: при развёрнутой панели остальные панели этой раскладки не проходят tick, хотя WS-подписки остаются. Таким образом фоновые fetch/таймеры этих панелей приостановлены. Это явная текущая политика; если обещание — «все панели всегда живые», стоит отделить обновление данных от рисования. Нужно проверить сценарий дополнительного CVD/ref-history при длительной максимизации.

## Что уже хорошо и что проверять дальше

Есть защита от полного Corrupt state, точечная санация, отдельные recovery outcome и предупреждения, rolling backup, fsync временного файла, тесты миграций и сохранения поддерживаемых индикаторов (`data/src/lib.rs:1043–1790`). Тест `1773` проверяет только успешное сохранение, отказ Windows-замены не моделируется. Общие подписки и маршрутизация вкладок — удачная основа; переписывать их целиком не требуется.

Рекомендуемый безопасный цикл поставки: отдельный профиль state/cache для проверки → сборка с manifest (commit/hash/дата) → проверка копии реального state без удаления индикаторов/панелей → штатное закрытие рабочей программы → датированный snapshot exe/state → установка → ручная проверка пользователем. Текущий exe в app-dev сам по себе не доказывает, какой commit установлен. Автоматические обновления и произвольный reset рабочего дерева для отката исключить.

Граница выводов: визуальная корректность окон, фактическая производительность и восстановление после потери сети не проверялись; для этого нужны отдельные воспроизводимые сценарии на изолированном профиле. Номера строк относятся к текущему состоянию исходников.
