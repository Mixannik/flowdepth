## FD-001 / WS-03: безопасное восстановление, 02.11.2026

Согласованные внутренние контракты реализованы поверх WS-01/02 (локальный diff, база `4c4be32`). `Event::RecoveryEvidence` несёт WsSource (session/generation/main-aux) и отдельный TradesResumed либо BookSynchronized (UTC/sequence). Подтверждение проходит через ту же проверяемую FIFO строго после доставленного payload; переполнение самого подтверждения завершает поколение по WS-01. TradesResumed не означает полноту истории. Current book proofs включены только для проверенных существующих путей Binance/MEXC (snapshot + проверенный buffered diff) и Hyperliquid (полные снимки публикуемой глубины). Bybit/OKX пока не выдают такого доказательства и автоматически не разблокируются.

Book proofs хранятся по точному StreamKind, включая параметры depth-подписки: два стакана одного тикера не подтверждают друг друга. Потеря инвалидирует только current-proof соответствующего потока; исторические faults не удаляются. Смена quantity-context или удаление подписки отбрасывает её доказательства. Ladder снимает предупреждение текущего стакана только по своему proof. Heatmap сохраняет предупреждение потерянной depth-истории; raw-детекторы остаются заблокированы. Текущий snapshot не объявляется replay истории.

Для trade recovery введён RecoveryToken: потерянные session/generation, successor, revision WS-02, symbol/stream, quantity-context, UUID панели и её привязки, точный полуоткрытый диапазон. Левый край берётся от доставленного до потери trade-watermark с учётом известных потерянных payload; без известной границы восстановления нет. Диапазон расширяется до целых бакетов от floor(left) до конца бакета первого возобновлённого batch; запрос начинается лишь после доставленной сделки за этим концом. Это сохраняет обе граничные миллисекунды и исключает гонку с формирующимся бакетом. Старый token, повторный overflow, смена источника/панели/единиц отменяют jobs или отсекают queued результат.

Совместимое автоматическое восстановление time-based KlineChart включено для Binance Spot/Inverse: свежие REST aggTrades с startTime включительно, затем fromId=last_id+1, без сдвига курсора на следующую миллисекунду. Проверяются последовательность ID, порядок времени, конфликты/дубли, валидность записей и наличие witness с временем >= правого исключённого края. Старый cache coverage/обычный Completed не являются доказательством; этот путь кэш обходит и не переписывает его. Контракт курсоров сверён с [Binance Spot](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market) и [COIN-M](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-coin-m-futures/api/rest-api/market-data). Binance Linear live использует raw trades: aggregate REST не доказывает восстановление его точных timestamps/order/size, поэтому такой consumer остаётся заблокированным. Ликвидации, raw sequence, tick charts, другие trade-источники и режим внешнего сервера автоматически не восстанавливаются.

Применение полного источника атомарно на уровне приложения: сначала проверяются consumer/token/source/context, наличие всех бакетов и совместимость сохранённых live-records с REST; затем заменяется только диапазон, пересчитываются footprint/POC и производные индикаторы. Live/history overlap не суммируется; соседние бакеты и корректные записи за пределами диапазона сохраняются. Снятие блокировки касается только восстановленного chart instance. Новая ранее отсутствовавшая поздняя сделка, смена basis/tick size или сброс модели отзывают proof. Partial/error/unsupported, конфликт, неизвестные границы, отсутствие witness/бакетов или превышение лимита ничего не очищают и блокировку не снимают. Лимиты: 2 параллельных jobs, 60 секунд, 128 страниц/100000 ответных записей; модель до 50000 raw-записей и 1000 полных бакетов. Ошибки повторяются не чаще раза в 30 секунд для того же consumer/token-range.

### A2b: восстановление без перезаписи оригинала

Реализован явный путь сохранения восстановленной сессии: загрузчик → layout → приложение. При предупреждениях исходный saved-state не переписывается ни при загрузке, ни при выходе; текущая сессия сохраняется отдельно в `saved-state.session-*.json`.
Неизвестные поля, которые serde раньше игнорировал, определяются по отсутствию в сериализуемой модели и тоже включают защиту. Исходные неизвестные настройки остаются в оригинале и защищённой копии, а не в адаптированной модели сессии.
Копия оригинала обязательна для recovery/migration; если её создать не удалось, существующий экран ошибки загрузки запрещает обычное автоматическое сохранение до явного выбора пользователя.
Предмиграционные, восстановленные и сессионные файлы исключены из обычной ротации; сессионные сохранения используют свой rolling backup и не затирают backup оригинала.
Ограничение: отдельная восстановленная сессия не становится основной автоматически. Следующий запуск снова читает оригинал; выбора/управления восстановленными сессиями в UI пока нет. Предупреждение сообщает путь сохранения.
