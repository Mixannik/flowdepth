# Айсберги — исследование (30.10.2026)

Айсберг — лимитная заявка, у которой в стакане видна только часть («пик»); после исполнения пика
биржа выставляет следующую часть на ту же цену. На Binance **спот** поддерживает такие заявки нативно
(`icebergQty`); на USDⓈ-M перпе нативных айсбергов нет, тот же эффект дают алго-заявки и маркет-мейкеры,
которые перезаливают уровень.

## Главное: детектор в коде уже есть

Пришёл из апстрима (коммит `d282d5f feat: add adaptive volume bubbles and iceberg detection`),
у пользователя **ни разу не включался** (в `saved-state.json` и логах нет `iceberg`).

- Ядро: `data/src/orderflow/iceberg.rs` (~1400 строк, без iced), реестр детекторов: `src/connector/iceberg.rs`,
  рисование: `src/chart/heatmap.rs` (треугольники ▲ «Possible buy iceberg» / ▼ «Possible sell iceberg», подсказка
  при наведении), настройки: `src/modal/pane/settings.rs` → окно настроек **хитмапа** → «Possible iceberg
  markers (Binance Linear)». Подробное описание апстрима: `docs/binance-iceberg-detector.md`.
- Входы: сырые сделки `<symbol>@trade` (на перпе вместо `aggTrade`, есть id и сторона агрессора) и
  `<symbol>@depth@100ms` с REST-снимком (`limit=1000` перп / `5000` спот) и проверкой непрерывности (`pu`/`u`);
  при разрыве эпизоды сбрасываются.
- Учёт перезалива на каждой цене у края стакана (≤2 тиков от лучшей цены):
  `ожидалось = видимо_до − исполнено`, `перезалито = видимо_после − ожидалось`, необъяснённое уменьшение = отмена.
- Срабатывание (по умолчанию): ≥3 цикла перезалива, исполнено/пик видимого ≥ 2.5, доля перезалива ≥ 0.5,
  цена ушла против уровня не больше 1 тика, балл ≥ 70 из 100. Порог размера адаптивный (p75 сделки за 60 с,
  25% медианной глубины у края), BTC-констант нет.
- Есть запись/повтор JSONL (`OrderFlowRecorder`, `replay_jsonl`), но в приложение **не подключены**.

## Как делают другие

| Где | Метод | Данные |
|---|---|---|
| Bookmap (CME) | Native: исполнение на цене + мгновенное появление новой заявки там же; «сделка больше видимого» — избыток считается айсбергом | MBO (по заявкам) надёжно; MBP (по уровням) — с задержкой до следующего исполнения |
| Bookmap (крипта) | Свой детектор для крипты выключали: «айсберги в крипте ведут себя по-разному на каждой бирже» (их разработчик на форуме) | — |
| ATAS | Встроенного для крипты нет (просят в фидбеке); сторонний TTW Iceberg Detector — по MBO | MBO |
| Kingfisher TOF | Серия одинаковых по размеру исполнений на одной цене | Лента |
| TradingView-скрипты | Свечные эвристики (тени, повторные тесты, всплеск объёма) | Свечи — слабо |
| MMT, Coinglass, Exocharts, Hyblock | Публичного описания детектора айсбергов не нашёл; у JDK в собранных материалах про айсберги ничего | — |

Общий признак везде один: **на цене исполнилось заметно больше, чем было видно, а уровень держится**.
Binance не даёт MBO (идентификаторов заявок), так что доступен только вариант MBP — ровно то, что сделано в коде.

## Что отдаёт Binance и хватит ли

- Перп: `@depth@100ms` (также 250/500 мс), дельты по уровням; REST-снимок до 1000 уровней. **RPI-заявки
  (Retail Price Improvement) в обычном потоке скрыты**, для них отдельный поток `@rpiDepth`.
- Спот: `@depth@100ms` (или 1000 мс), REST до 5000 уровней, сырой `@trade` тоже есть; у нас на споте пока `aggTrade`.
- 100 мс — это нетто-изменение уровня за 100 мс: несколько «съели–перезалили» внутри окна сливаются в одно.
  Для «исполнено против видимого» на одной цене этого **хватает** (сделки идут поштучно, их сумма за окно
  сравнивается с изменением уровня), но счёт циклов и задержка перезалива грубые — минимум 100 мс.
- Истории стакана по уровням у Binance нет (в архивах data.binance.vision только сжатый `bookDepth` по
  процентным диапазонам — для одной цены бесполезен) →
  на прошлых свечах айсберги не восстановить, только live (и с момента открытия хитмапа).

## Ограничения и ложные срабатывания

1. **RPI на перпе** — скрытая ликвидность у края, которая исполняется против розничных заявок: в ленте сделки есть,
   в стакане объёма нет → выглядит как «исполнено больше видимого». Главный кандидат на ложняк у Binance-перпа.
2. Маркет-мейкеры котируют уровень заново после каждого исполнения — тот же рисунок, но не «крупный игрок».
3. Несколько независимых заявок на одной цене, быстрые отмена/перевыставление.
4. Только одна биржа: айсберг может стоять на Bybit/OKX/споте, а мы видим перп Binance.
5. Подтверждается после 3 циклов — то есть уже по ходу; конец айсберга (снятие) по MBP почти не виден.
6. Детали форка: детектор кормится только из **активной** раскладки (`main.rs`, `active_dashboard()`), маркеры
   живут 5 мин (`retention_seconds`), не сохраняются, видны только на хитмапе, спот не поддержан.

## Рекомендуемый простой вариант

**Шаг 0 — без кода (сделать первым).** Открыть хитмап BTCUSDT перп в отдельной вкладке, включить
«Possible iceberg markers», поднять слайдер хранения маркеров (по умолчанию 5 мин) и пару дней
смотреть: сколько маркеров, где (у уровней или везде), держится ли цена после них. Это самая дешёвая проверка,
есть ли от детектора толк, — бритва Оккама.

**Шаг 1 — если маркеры осмысленные, перенести их на футпринт** (минимум кода, данные уже есть):
- раздавать `IcebergEvent` графикам свечей того же тикера, как уже раздаются уровни FRVP
  (`set_shared_range_levels`) — и брать детектор со всех вкладок, а не только активной;
- рисовать в ячейке футпринта на цене события: рамка/значок цвета стороны (зелёный — покупатель-айсберг на биде,
  красный — продавец на аске), размер по `aggressive_executed_qty`; подсказка: исполнено / пик видимого / циклы / балл;
- хранить события в памяти графика (не 5 мин, а пока свеча на экране), в state ничего нового.

**Шаг 2 — по желанию.**
- Подключить `OrderFlowRecorder` (флаг уже есть) и проверить события на истории так же, как failed auctions
  (против случайных входов), прежде чем делать сигнал.
- Галочка «Iceberg» в Signals → Only near levels: оставлять только события у FRVP/period/naked/VWAP уровней —
  это резко срежет шум маркет-мейкеров.
- Спот: перевести спот на `@trade` и снять ограничение «только Linear» (спот-айсберги нативные, их рисунок чище;
  RPI на споте нет).
- Сравнение «без стакана» (запасной вариант): за свечу на цене объём сделок ≫ средний объём строки при цене,
  не ушедшей за уровень, — это уже почти наш Absorption в `signals.rs`; айсбергом без стакана это не доказать.

Пороги менять только после шага 0 — по умолчанию разумные (3 цикла, ×2.5, балл 70).
