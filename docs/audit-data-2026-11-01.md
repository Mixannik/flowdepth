# Аудит данных Flowdepth — 01.11.2026

Статический разбор локального кода; рабочие данные и процессы не менялись, тесты в этом аудите не запускались.

## Как проходит информация
- `exchange/src/adapter/hub/binance/{stream,fetch}.rs`: WebSocket для live, REST/дневные ZIP для истории; нормализация цены, объёма, стороны и времени на входе.
- `src/connector/fetcher.rs`: заявки диапазонов, отмена/повторы, чтение кэша, загрузка дыр, выдача порциями. `RefTrades` использует тот же путь, но собирает результат целиком перед передачей индикатору (:2352).
- `src/connector/persistent_cache.rs`: redb, версия схемы, checksum/семантическая проверка, минутные корзины сделок, покрытие диапазонов и поиск длинной тишины.
- `data/src/chart/kline.rs`: сделки → ценовые строки/статистика свечи; сжатие и корзины CVD размера; после 2 суток дисковый кэш хранит агрегаты вместо исходных сделок.

## Подтверждённые риски
1. **P1: блокировка базы ошибочно считается повреждением.** `persistent_cache.rs:445–453` на любую ошибку открытия переносит существующий файл в `.corrupt-*` и создаёт новый. В `:1425` при неудачном переносе пробует удалить файл. Второй экземпляр способен отцепить исправный кэш первого; реальный лог этого запуска уже содержал `cause=Database already open`. Исправление: сохранить тип ошибки redb, lock/permission/IO не лечить пересозданием; отдельно блокировать второй экземпляр.
2. **P1: единица объёма отсутствует в ключе кэша.** `persistent_cache.rs:1439–1444` содержит только схему/биржу/символ/тип данных; Binance fetch нормализует объёмы согласно глобальному режиму (`fetch.rs:446–476`, `:630–643`, `:739–763`). Один диапазон, записанный в USD, может читаться в режиме BTC и наоборот. Правильная цель — каноническое хранение и перевод для отображения; переход требует миграции/инвалидации.
3. **P1: сжатие частей минуты не эквивалентно сжатию полной минуты.** `fetcher.rs:2744–2752` сохраняет отдельные полученные порции; `persistent_cache.rs:578–580` агрегирует каждую независимо. Синтетический ID зависит от минуты/ценовой строки/стороны/корзины (`data/src/chart/kline.rs:500–509`), но не исходного диапазона. При совпадении ID `Trade::normalize` оставляет только первую запись (`persistent_cache.rs:297–304`), вместо суммирования частей. При разных high/low частей могут также остаться разные агрегаты одного диапазона. Влияние на реальную историю ещё не измерено; нужен тест: загрузка одной минуты целиком против двух непересекающихся порций и последующего расширения диапазона.
4. **P2: проверка дыр не проверяет пустую/одноэлементную покрытую историю.** `persistent_cache.rs:1596–1603` сразу возвращает пустой список. Такая проверка не исправит legacy coverage, если выборка полностью пуста. Это ограничение именно эвристики тишины: другие проверки bucket/coverage работают отдельно. Не считать любую пустоту биржи ошибкой; сверять с OHLCV и доступностью источника.

## Смысловые ограничения
- Сжатие старше 2 суток теряет точный порядок сделок, число исполнений и часть ценовой детализации; сохранение high/low и корзин не делает историю полностью равной raw. Комментарий `persistent_cache.rs:568` «footprint is unchanged» слишком сильный.
- CVD по размеру группирует одну сторону в одну миллисекунду (`data/src/chart/kline.rs:343`): это приближение заявки, не биржевой order ID. Названия «ретейл/киты» — интерпретация объёма, не идентификация участников.
- Найдено 35 атрибутов тестов в трёх рассмотренных файлах: есть проверки размера CVD после агрегации, архивного времени/стороны, тишины и кэша. Нужны отдельные проверки lock ≠ corruption, смены BTC/USD и независимости агрегирования от границ загрузки.
